# Part 3 독립 의미 검토

검토일: 2026-10-15. 결론: 전체 문항 읽기에서 확인된 정답 키 오류·복수 정답·위험한 보편 명제를 정답으로 삼은 문항은 발견하지 못했다. 통합을 막을 P1 사실 오류는 보고하지 않는다. 다만 변별력을 떨어뜨리는 오답 보기와 WEP·LM의 원인 설명에 아래 세 가지 개선을 권고한다. 이는 모든 명제의 학술적 진실성을 보증한다는 뜻이 아니다.

이 작업은 읽기 전용 콘텐츠 리뷰다. 검토 대상 JSON·Part 3 감사 문서·저작 소스·구현은 수정하지 않았다. 이 문서만 작성했으며, 추가 지시에 따라 별도로 소유한 `docs/content-audit-part-4.md`의 로컬 절대 경로만 정리했다. 브라우저·CI·배포는 부모 담당이며 이 리뷰의 검증 결과가 아니다.

### PR3-01 [P2, 평가 품질] 무관한 분야의 오답으로 쉽게 제거되는 문항

직접 확인한 취약 표본: `w09-q017`, `w09-q024`, `w09-q049`, `w10-q014`, `w10-q018`, `w10-q033`, `w11-q014`, `w11-q021`, `w11-q022`.

정답은 현재 타당하다. 문제는 나머지 세 보기가 질문의 기술 경계와 거의 관계가 없어서 이해하지 않아도 정답을 고를 수 있다는 점이다. 예를 들어 `w09-q049`는 승인된 계정·설치·변경 기록을 묻는데 배경색·키보드 배열·가장 긴 파일명을 오답으로 둔다. `w11-q014`는 위험 평가인데 글자 수·표 높이·화면 색상만 오답이다. `w11-q022`의 서버 세션 무효화도 버튼 색·제목 길이·메뉴 순서로 비교해, 로컬 상태 제거와 서버 무효화의 실제 혼동을 평가하지 못한다.

권고는 정답 교체가 아니라 동일 개념 안의 그럴듯한 오개념으로 보기와 해설을 다시 쓰는 것이다.

### PR3-02 [P2, 인과 설명·적용 범위] WEP IV 재사용의 결과를 실제로 설명하고 질문하기

대상: `w10-wep`, `w10-q026`~`w10-q030`, `w10-wep-structure`, `w10-iv-count`. 직접 관련 원문: 10주차 23·24쪽.

현재 WEP 목표는 공개 IV, 비밀 키 부분, ICV와 CRC, 긴 키만으로 해결되지 않음, 고정 프레임 수로 복구를 보장할 수 없음을 정확하게 구분한다. 그러나 반복 IV와 키스트림 재사용이 왜 내용 보호를 깨는지는 이름을 나열하는 데 가깝다. 유일한 풀이 예는 64에서 공개 24를 나누는 키 길이 해석이고, 다섯 문항 중 이 반복의 인과 관계를 직접 설명·적용하는 문항은 없다. 따라서 페이지 대응은 있지만 이 핵심 하위 주제의 교육 깊이는 얕다.

권고: 같은 비밀키와 같은 IV라는 조건에서 같은 키스트림이 다시 사용되는 이유를 설명하고, 두 암호문에 공통 보호 마스크가 반복되면 평문 간 관계가 드러날 수 있다는 안전한 기호·가상 데이터 예를 추가한다. IV 재사용만으로 모든 비밀키가 즉시 복구된다는 결론과는 분리한다. 실제 수집·주입·복구 코드나 도구 명령은 필요 없다. `w10-q029`의 고정 성공 보장 반박을 유지하되, 별도 문항 또는 기존 문항 개작으로 같은 키/다른 키·같은 IV/다른 IV의 조건을 비교하게 한다.

근거: [NIST SP 800-97, §3.2.2, 문서 3-4~3-5쪽](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-97.pdf)은 공개 IV·재사용·같은 IV를 가진 메시지 사이의 내용 노출을 설명한다. 이 문서는 철회된 역사 자료이며 여기서도 WEP 구조 확인에만 사용한다. [철회 안내](https://csrc.nist.gov/pubs/sp/800/97/final)를 함께 확인했다.

이 항목은 현재 정답의 오류가 아니라 학습자가 원인을 설명하도록 만드는 보강 권고다. `w10-q026`의 정답 40비트와 `w10-q027`의 정답 Data+ICV는 변경할 이유를 찾지 못했다.

### PR3-03 [P2, 원문 오류 정정의 완전성] LM 그림의 추가 한 바이트와 독립 분할을 명시적으로 정리

대상: `w09-password-storage`, `w09-lm-history`, `w09-q041`, `w09-q043`. 직접 관련 원문: 9주차 23쪽 그림.

현재 콘텐츠는 해당 그림이 현대 모든 Windows의 저장 형식이 아니라 구형 LM 사례임을 올바르게 고쳤다. 8자/7자의 고정 두 배, 리눅스 한 글자마다 고정 백 배 주장도 점수화하지 않는다. 그러나 원문 그림의 ‘7 byte + 패스워드 데이터 1 byte’라는 표기를 직접 해명하지 않아, 원문을 병행하는 학습자가 LM에서 매 블록에 추가 비밀번호 바이트가 붙는다고 이해할 여지가 남는다. 현재의 ‘두 부분을 별도로 다룬다’는 문장도 왜 전체 비밀번호를 한 덩어리로 추측하는 것과 다른지 예시로 풀지 않는다.

권고: 역사적 LM 설명에 대문자 변환·14자리 범위의 패딩·두 7바이트 부분의 별도 처리라는 조건을 명시한다. 원문 그림의 한 바이트를 추가 비밀번호 데이터로 읽지 말고, DES 키의 유효 비트와 패리티를 분리해 설명한다. 두 독립 절반 때문에 긴 하나의 후보 공간과 다른 추측 구조가 된다는 가상 예를 넣되, 실제 해독이나 고정 시간·배수는 계산하지 않는다. `w09-q041`의 역사적 분류 정답은 유지하고 추가 회상/비교 질문으로 구조 이해를 확인한다. 원문처럼 모든 언어의 ‘문자 수’가 곧 바이트 수라는 일반화도 피한다.

근거: [Microsoft MS-NLMP §3.3.1](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-nlmp/464551a8-9fc4-428e-b3d3-bc5bfb2e73a5)은 대문자 변환 후 앞·뒤 범위를 별도로 처리하는 LMOWFv1을 정의한다. [Microsoft Passwords technical overview의 LM 계산 절](https://learn.microsoft.com/en-us/windows-server/security/kerberos/passwords-technical-overview)은 두 7바이트 키와 각 결과의 결합을 설명한다. [MS-LSAD의 DES-ECB-LM 정의](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-lsad/32a2c8af-dc6e-4662-918d-ef333d570dd2)는 7바이트 입력의 8바이트 DES 키 표현과 패리티 비트를 구분한다. 해당 개요 문서의 과거 기본 저장·옛 비밀번호 권고까지 현행 보편 지침으로 가져오지는 않는다.

이것도 배포 JSON에 잘못된 추가 바이트를 정답으로 넣었다는 뜻은 아니다. 원문 그림을 완전히 바로잡고 WHY 설명을 완성하라는 권고다.

## 하위 주제 커버리지 판단

전체 JSON의 목표·문항·coverage를 읽었을 때 큰 단원이 통째로 사라진 사례는 발견하지 못했다. 9주차의 네트워크 관찰·위조·가용성·시스템·인증·계정·메모리·포맷, 10주차의 무선 구조·위협·발견·수신 조건·주소 필터·WEP·WPA, 11주차의 HTTP·URI·위험 판본·서버 경계와 교안 위험 항목은 각각 실제 설명에 대응한다.

다만 이는 79쪽 원문 전부의 독립 대조 결과는 아니다. JSON상 원문 페이지 집합이 28/28/23으로 모두 대응하고, 표본 10쪽의 큰 주제가 설명에 반영됨을 확인한 것이다. 11주차 23쪽의 blank 상태는 원래 감사 문서의 확인을 읽었으며, 이번 리뷰에서 해당 페이지를 새로 시각 검증하지 않았다.

교육 깊이에서 가장 필요한 보강은 PR3-02·03이다. 또 HTTP의 OPTIONS·TRACE·PUT·DELETE는 본문에서 다루지만 문항은 POST/HEAD와 일반 인가 구분에 치우친다. 추가 문항 수를 늘리기보다 이후 일부 반복적인 보안 경계 문제를 실제 메소드 의미 비교로 교체하는 것이 유용하다. 공식 2017 최종판의 역직렬화는 명시된 현대 보충이며 원문 위험 단원을 대체하지 않는 범위로 이해했다.

HTTP 보강도 기존 수량 안에서 수행했다. `w11-q003`은 PUT/POST/OPTIONS/DELETE 네 실제 메소드를 비교한다. 목표의 비교표·풀이에서는 HEAD·OPTIONS·TRACE의 서로 다른 목적과 DELETE가 모든 물리적 복사본 삭제를 보장하지 않는다는 경계를 함께 설명한다. 메소드 지원이 인가나 전송 보호를 보증한다는 주장은 정답으로 쓰지 않는다.

### 1차 출처 확인과 한계

- [Microsoft MS-NLMP §3.3.1](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-nlmp/464551a8-9fc4-428e-b3d3-bc5bfb2e73a5)을 이번 구현에서 재방문하여 대문자 변환·짧은 값의 0 패딩·두 범위의 별도 계산을 확인했다. 인코딩 일반화 대신 예를 ASCII로 한정했다.
- [Microsoft MS-LSAD §5.1.3](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-lsad/32a2c8af-dc6e-4662-918d-ef333d570dd2)을 이번 구현에서 재방문하여 7바이트 입력의 8바이트 DES 키 표현과 패리티를 확인했다. 원문의 23쪽 추가 바이트 표기를 바로잡는 근거로 정정에 직접 연결했다.
- [RFC 9110 §9.3.3~9.3.8](https://www.rfc-editor.org/rfc/rfc9110.html)을 이번 구현에서 재방문하여 POST/PUT의 요청 의도 차이, 클라이언트가 지정한 대상 URI, DELETE의 연결 제거 의미를 대조했다. 기존 HTTP 메소드·인가 경계의 출처를 유지했다.
- [역사적 NIST SP 800-97 §3.2.2](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-97.pdf)의 최초 리뷰 선택 독해 근거를 유지했다. 이번 재조회에서는 PDF 본문에 타임아웃/403이 발생하여 본문을 새로 완독했다고 주장하지 않는다. [NIST 상태 페이지](https://csrc.nist.gov/pubs/sp/800/97/final)는 이번에 다시 열어 2025-12-31 철회를 확인했다. 문서는 역사적 구조 확인용이며 현재 운영 권고가 아니다.
- WEP의 `C1 XOR C2 = P1 XOR P2`는 같은 마스크를 사용한다는 전제에서 직접 유도한 교육용 등식이다. 4비트 예는 `1001 XOR 1111 = 0011 XOR 0101 = 0110`으로 직접 확인했다. 실제 키·IV·프레임·복구 실행 예가 아니다.

이번 수정에서 원문 교안 79쪽이나 모든 외부 문헌을 재독하지 않았다. 원문 독립 대조 범위는 위 최초 리뷰의 10쪽·세 이미지 표본 그대로다. 변경 전 140문항 전체 읽기와 변경 후 발문·네 보기 재검토는 수행했지만 학습자 대상 난이도·변별도 실험 또는 모든 명제의 전수 문헌 검증은 아니다. PDF skill의 구조 텍스트와 시각 근거 구분을 유지했으며 새 PDF·이미지나 실행 공격 예를 앱에 추가하지 않았다. 미확인 역사 사건 상세와 구형 도구의 현재 호환성은 기존 비채점 한계를 유지한다.

### 테스트 순서와 최종 인계

콘텐츠 수정 전에 회귀 테스트 6개를 먼저 작성하여 실행했고 0통과/6실패를 확인했다. WEP 조건·풀이·복구 한계, 같은 IV/다른 키 및 같은 키/다른 IV의 구분, LM 패리티·독립 분할, HTTP PUT 비교, 무관한 보기 잔존을 검사한다. 수정 후 동일한 6개가 모두 통과했다. 정규식 검사는 핵심 교육 경계의 회귀 방지이며 사실성 자동 증명의 대체가 아니다.

최종 생성은 `node tools/authoring/part-3.mjs`로 수행하여 세 주차를 각각 `validateWeek()`로 검증했다. 쪽 대응, 목표당 최소 3문항, 고유 ID·발문, 네 개의 서로 다른 보기와 유효 정답을 확인했다. `node --test test/content-part3-regression.test.js` 6/6, `npm test` 63/63, `npm run check` 통과를 확인했다. 공유 작업 디렉터리에서 실행한 시점의 결과이며 부모의 브라우저 테스트·CI·배포 성공으로 확대 해석하지 않는다. 텍스트는 UTF-8 BOM 없음·CRLF를 유지했다.

PR3-01/02/03 구현에 남은 차단 항목은 없다. 남은 한계는 WEP PDF의 이번 본문 재조회 실패와 전수 문헌·학습자 실험·브라우저/배포 검증을 수행하지 않았다는 점이다. 게시·커밋·푸시·에이전트 생성은 하지 않았다. 부모의 콘텐츠 동결·통합 판단을 위한 완료 상태로 인계한다.
